# Voucher wallet / bulk distribution V32

Approved scope: customer UI/receipt/application (UC20/21/38), Admin programs (UC69/54), KTV issuance/revocation (UC70/55), durable audit foundation (UC77). User extension: quick filtering and multi-recipient operations. Full canonical multi-seller checkout, spending/refunding xu and central audit viewer remain separate backlog items.

Commerce owns voucher policies, receipts and checkout binding. Identity exposes typed staff/customer/search/ordered-lock facade. Platform exposes durable voucher command receipts and in-app outbox; no cross-module repository access. React feature `features/vouchers` replaces voucher local management store pages and keeps existing theme/outline primitives.

No new business table: existing vouchers row types, immutable revisions, product scopes, grants/events, orders and Platform audit/outbox carry the workflow. V32 adds parent `wallet_enabled` false for old programs (no retroactive auto-grant), order `wallet_grant_id` with unique index/FK, immutable voucher command receipt guard and campaign issuance guard. Old records are preserved. Admin saves enable wallet policy explicitly. Shared migrations V1–V31 remain unchanged.

Save creates an immutable revision containing title/description/self-claim plus benefit/date/conditions. Grants reference that revision; parent pause/edit controls future issuance only. Grant/revoke batch locks campaign then customers in numeric order, then grants. Checkout acquires buyer/seller locks before grant to match order/account lock ordering. Database guards protect campaign/per-customer limits and single consumption. Canonical redemption adapters are retained; a narrow physical-order-trigger bridge preserves the previous grant history validator while allowing validated buy-now consumption.

Command receipts use actor/action-scoped UUID keys, normalized JSON requests and persisted result. Preview makes no state transition. Execute revalidates current version and each item under locks. Unavailable rows skip with reason; unexpected persistence/outbox failure rolls back atomically. Receipt stores explicit IDs and reason, so retries cannot silently enlarge audience. Unique keys prevent repeat mutation/notice.

Migration: additive V32, lock timeout10s, statement timeout120s, no deletes/backfill of history. Before application rollout: stop only tracked backend, capture local private PG dump and fingerprints; verify restoring dump on dedicated clone; run V31→V32 there and compare all old physical/view sources excluding the two new columns; apply to app only after checks. Keep old jar for diagnosis. Forward-fix preferred if V32 accepted new voucher/orders; do not downgrade to an older application that bypasses owned grants. A database restore is only safe before new post-migration activity, otherwise preserve new history and apply a new migration.
